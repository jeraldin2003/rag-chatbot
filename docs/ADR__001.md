# ADR-001: RAG Chatbot v1 — Vector Store & Model Choices

**Scope:** Week 9 assignment

## Context
Assignment called for Qdrant or Pinecone as the vector DB, plus one API model and one Ollama model behind a toggle. We already had a Postgres connection set up, and needed to stay fast to build.

## Decision
- Used Postgres + pgvector instead of Qdrant/Pinecone, since we already had a DB connection and didn't want a second service to manage.
- Used Gemini for embeddings and as the API-based generation model, to avoid juggling two API keys.
- Built two separate routes (`/chat/gemini`, `/chat/ollama`) instead of one route with a provider flag — easier to test each independently.
- Switched Ollama's model from `llama3` to `qwen2.5:1.5b` after `llama3` took ~10 minutes per response on our hardware.
- Dedup by hashing the normalized extracted text, not the raw PDF bytes, so a re-saved copy of the same file is still caught as a duplicate.

## Alternatives Considered
- Qdrant/Pinecone — rejected, extra infra for no real benefit at this scale.
- Single `/chat` route with a provider toggle field — rejected, wanted routes we could hit independently in Postman.
- Returning top-K chunks unconditionally — rejected after an irrelevant query still returned confident-sounding chunks; added a similarity threshold instead.

## Consequences
- Simple to run (one DB), but pgvector won't scale as well as a dedicated vector DB if the doc set grows a lot.
- `qwen2.5:1.5b` is fast but noticeably weaker/more hedging than Gemini.
- No conversation memory yet — every question is independent.
