# ADR-003: Migrate Vector Store from pgvector to Qdrant

**Scope:** Retrieval infrastructure

## Context
ADR-001 chose Postgres + pgvector over Qdrant/Pinecone to avoid running a second service. Since then we added hybrid search using Postgres full-text search as a BM25 stand-in, and need a clearer path to proper hybrid search and re-ranking (Week 10 requirement).

## Decision
Migrate the vector store to Qdrant.

## Alternatives Considered
- Stay on pgvector + Postgres full-text search — rejected, Postgres has no native BM25; `ts_rank_cd` is an approximation, not the real algorithm.
- Pinecone — rejected, no self-hosted option and adds a paid dependency.
- Add a separate BM25 engine (e.g. Elasticsearch) alongside pgvector — rejected, two services to run instead of one.

## Consequences
- Qdrant has built-in BM25 (via its sparse vector / full-text support), removing the need for a Postgres full-text workaround.
- One less reason to keep Postgres in the retrieval path — adds a migration cost (re-embedding and re-inserting all existing chunks).
- Introduces a new service to run and operate, which ADR-001 originally avoided.
